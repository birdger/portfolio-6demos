# PRD: AI 商品推荐助手 (proj6-ai-agent)

> 定位：**AI 产品经理能力证明**。不是"接个 API 聊两句"，而是把 RAG 检索、Agent 工具调用、
> 幻觉兜底、**量化评测**、token 成本核算这五件事做成可点开、有数字、能自证的系统。
> 说明：本项目为个人自研课题 Demo（与本人科研方向 *多模态推荐 / LLM 富化* 同源），
> 非任何公司项目；商品语料使用公开的 Amazon Reviews 2023 (All_Beauty) 数据集。

## 1. 背景与问题

电商/内容平台的商品库普遍存在两类问题：

| 问题 | 现状 | 后果 |
|---|---|---|
| **信息稀疏** | 商品标题短、属性缺、描述是商家随便填的 | 搜索召回差、推荐冷启动难 |
| **交互僵化** | 只能"关键词 + 筛选器"，用户得自己拆解需求 | 长尾需求（"油皮夏天用的清爽防晒"）无法表达 |

大模型给了新解法：用 LLM 把稀疏商品**富化**成结构化标签，再用 RAG 让用户用**自然语言**找货。

## 2. 目标用户与场景

- **主用户：消费者**。场景：不知道商品叫什么名字，只能描述需求 → 期望得到 3–5 个**有理由**的推荐，并知道"为什么推给我"。
- **次用户：平台运营**。场景：批量给商品生成标签，人工审核后入库；关心**花了多少钱、效果好不好**。

## 3. 范围

**做**：单轮/多轮问答式推荐、基于本地语料的检索增强、引用商品卡片、无答案时明确拒答、富化任务与审核、20 用例 × 2 模型的自动化评测、token 成本看板。

**不做**：用户画像与协同过滤（属推荐系统另一条线）、线上 A/B 实验平台、真实支付与交易、模型微调。

## 4. 核心功能

### F1 商品库（语料底座）
- 从本地 `All_Beauty.jsonl` 导入商品（可指定条数，默认 300 条用于演示，支持导入更多）
- 字段：ASIN、标题、品牌、价格、类目、描述、评分、评论数、图片
- 列表支持关键词搜索 + 类目筛选；详情页展示原始信息与富化结果

### F2 智能富化（LLM 结构化打标）
- 单条/批量（前 N 条）调用 LLM，输出结构化 JSON：`一句话卖点 / 适用人群 / 使用场景 / 关键属性标签`
- 落库保存，记录所用模型、token 用量、成本；失败自动降级为规则模板并标注
- 富化结果可人工编辑（体现"AI 生成 + 人工审核"的运营闭环）

### F3 对话式推荐（RAG + Agent）
- 用户自然语言提问 → **BM25 检索** Top-K 商品 → 组装上下文 → LLM 生成回答
- 回答必须**引用商品**（回答中带商品卡片/ASIN），前端渲染成卡片
- **幻觉兜底**：检索得分低于阈值 → 直接回复"语料中没有相关商品"，不编造
- 展示本次调用的检索命中、耗时、token、成本（可解释性）

### F4 评测中心（本项目的核心差异点）
- **20 条评测用例**（含 3 条"语料外问题"，专门测拒答）
- **2 个模型对比**（同一套检索结果，只换生成模型）
- 指标口径：
  - `命中率 Hit@K` = 期望商品出现在 Top-K 检索结果中的用例占比（**检索质量**）
  - `引用准确率` = 回答中引用的商品全部来自检索结果的比例（**幻觉率反向指标**）
  - `拒答正确率` = 语料外问题中正确拒答的比例
  - `平均延迟` / `平均 token` / `单次成本`
- 一键跑批 → 结果表格 + 对比柱状图 + 可导出的 Markdown 评测报告

### F5 成本看板
- 累计调用次数、token 输入/输出、总成本（分）
- 按模型、按功能（富化/问答/评测）拆分
- 单次问答成本、每千次成本预估

### F6 调用日志
- 每次 LLM 调用的完整记录：时间、功能、模型、耗时、token、成本、成功/降级

## 5. 关键设计取舍（面试可讲点）

| 取舍 | 选择 | 理由 |
|---|---|---|
| 向量检索 vs 关键词检索 | **BM25（纯 Python）** | 只允许 flask+stdlib，不引重型依赖；美妆语料短文本 BM25 已够用；评测数据可证明其 Hit@K |
| 检索结果要不要重排 | 先用 LLM 生成时的顺序，不额外重排 | 多一次调用 = 多一份成本与延迟，先用评测验证是否值得 |
| 幻觉怎么治 | **检索阈值 + 强制引用 + 拒答** | 与其让模型"编一个像样的答案"，不如承认不知道——可解释性 > 覆盖率 |
| 成本怎么控 | 限制上下文条数（Top-5）+ 输出 max_tokens | 上下文是成本主因；评测报告里给出"K=3/5/8"的成本-效果权衡 |
| LLM 不可用怎么办 | 离线兜底模式，明确标注 | Demo 必须随时能点开；且**评测报告如实标注运行模式**，不伪造指标 |

## 6. 成功指标（验收口径）

- 6 个页面全部可点开无报错；对话能返回带商品卡片的回答
- 评测中心能跑完 20×2 并产出**真实数字**（不是写死的），报告可导出
- 语料外问题能被正确拒答（不编造商品）
- 成本看板数字与调用日志能对上账

## 7. 风险

| 风险 | 应对 |
|---|---|
| 上游 LLM 接口不稳定/限流 | 超时 45s + 失败降级 + 日志留痕；评测分批串行避免限流 |
| 语料导入慢 | 默认只导 300 条，导入进度落库，支持增量 |
| 指标被质疑"自己给自己打分" | 指标口径写死在文档里，评测用例的期望值来自语料本身而非人工编造；报告公开每条用例的原始回答 |
